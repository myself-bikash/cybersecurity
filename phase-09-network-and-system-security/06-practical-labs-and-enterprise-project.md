# Practical Labs and Enterprise Project

## Safety and authorization

Use your own Linux or Windows computer or isolated virtual machines. Do not scan or test a network
without authorization. Keep vulnerable systems on a host-only or otherwise isolated lab network,
use synthetic data, and do not bridge them to production or public networks.

The exercises below preserve the PDF's learning objectives while avoiding instructions for
unauthorized access, exploit activity, or scanning beyond the designated lab.

## Practical exercises

### 1. Local network discovery and traffic analysis

**Source tools:** Nmap and Wireshark.

On your own computer or lab VM, document local network interfaces and services, capture traffic
generated by your own benign test activities, and identify examples of DNS, TCP, and HTTPS-related
traffic. Record the observed services and protocols. Do not scan other devices or networks.

**Expected learning:** network architecture, interfaces, services, ports, protocols, and packet
analysis.

### 2. Firewall security

**Source tools:** UFW or Windows Firewall.

Review the local firewall status and rules; identify unnecessary exposed services; apply a test
policy in a disposable VM; verify only intended services remain available; and document changes.
Keep a recovery path so a test rule cannot lock you out.

**Expected learning:** firewall architecture and network access control.

### 3. IDS and network monitoring

**Source tools:** Suricata or Zeek.

In an isolated lab, review setup guidance, examine traffic generated by benign lab activity, analyze
resulting logs, identify DNS requests and connection attempts, review safe test alerts, and document
normal versus suspicious-looking activity. Do not generate attack traffic against a third-party
network.

**Expected learning:** network intrusion detection and monitoring.

### 4. Linux hardening

On your own Linux system or VM, review accounts, file permissions, running services, SSH
configuration, firewall policy, and available security updates. Run a security audit using Lynis if
available. Make changes only after confirming a recovery route.

**Expected learning:** Linux system hardening.

### 5. Windows hardening

On your own Windows system or VM, review Defender, Windows Firewall, local accounts, updates,
startup applications, security events in Event Viewer, and BitLocker availability. Document
improvements without publishing sensitive event or account data.

**Expected learning:** Windows system hardening.

### 6. Vulnerability management

Use a provided sample report or a deliberately vulnerable VM whose lab instructions explicitly
authorize assessment. Review findings and CVE references, understand severity ratings, prioritize
remediation, apply a fix, and verify the result. If the lab permits a vulnerability scanner, target
only the specific isolated system designated by the lab; do not scan public or shared networks.

**Source tools:** Greenbone/OpenVAS or Nessus Essentials, where available.

**Expected learning:** vulnerability assessment, prioritization, remediation, and verification.

## Major practical project: Enterprise Network Security Lab

Build a small enterprise network in a virtual lab and secure it.

### Proposed architecture

| System | Purpose |
| --- | --- |
| Kali Linux VM | Authorized security testing within the isolated lab only. |
| Ubuntu Server VM | Linux server to harden and monitor. |
| Windows VM | Windows endpoint to harden and monitor. |
| Firewall VM | Network traffic control. |
| IDS/IPS | Network threat detection. |
| Monitoring system | Log collection and analysis. |

Keep the lab isolated. The source's example recommends starting with two or three lightweight VMs
and adding systems gradually rather than running every VM simultaneously; scale to the host
computer's available resources.

### Project stages

| Stage | Task |
| --- | --- |
| 1 | Design the network topology. |
| 2 | Configure lab network interfaces. |
| 3 | Configure firewall rules. |
| 4 | Create network segments. |
| 5 | Harden Linux. |
| 6 | Harden Windows. |
| 7 | Configure IDS monitoring. |
| 8 | Implement secure remote access. |
| 9 | Review a vulnerability assessment for authorized lab systems. |
| 10 | Collect and analyze logs. |
| 11 | Investigate synthetic or safe lab activity. |
| 12 | Document findings and improvements. |

For assessment and monitoring stages, use only the lab's designated systems and allowed
activities. No exploit steps or commands are part of this project.

### Final project deliverables

1. Network architecture diagram.
2. IP address and subnet plan.
3. Firewall configuration report.
4. Linux hardening report.
5. Windows hardening report.
6. IDS/IPS monitoring evidence.
7. Vulnerability assessment report.
8. Network monitoring evidence.
9. Backup and recovery plan.
10. Final security assessment.

## Project review checklist

- [ ] Lab topology and authorization are documented.
- [ ] Vulnerable systems are isolated.
- [ ] Firewall rules permit only required lab communication.
- [ ] Linux and Windows hardening changes are documented.
- [ ] IDS/IPS and monitoring events are collected from benign or simulated activity.
- [ ] Vulnerability assessment is limited to expressly authorized lab targets.
- [ ] Findings include remediation and verification.
- [ ] Logs and reports do not expose credentials or personal data.
- [ ] Backup and recovery assumptions are tested or clearly identified as untested.

**Lesson deliverable:** submit the isolated-lab diagram, one completed exercise record, and a
sanitized final assessment that states scope, evidence, changes, verification, limitations, and
recovery status.

## Review questions

1. What must be established before assessing a system or network?
2. Why should vulnerable VMs be isolated from production and public networks?
3. How do IDS monitoring and firewall enforcement differ?
4. What evidence should a vulnerability-management report include?
5. Why should backups be restored in a test rather than merely counted?

### Answer key

1. Ownership or explicit authorization and a clearly defined scope; this prevents impact outside
   the approved lab.
2. Isolation limits unintended exposure and prevents lab activity from affecting other systems.
3. IDS observes and alerts; a firewall enforces traffic policy.
4. Scope, sanitized findings, severity/context, remediation, verification, and limitations support
   safe, actionable follow-up.
5. A restore test confirms that copies and procedures can actually recover data and services.
