# Course Guide

Welcome. You can start without previous cybersecurity knowledge. The course first builds the
language and system models that make later security topics easier to understand, then uses safe
projects to practice sound judgment.

## How to learn here

Use the same short loop for each lesson:

1. **Preview:** read the objectives and note one question you want answered.
2. **Understand:** follow the explanation and trace the example from input to outcome.
3. **Try:** perform the exercise only in its stated authorized environment. If you cannot run a
   lab, use the synthetic scenario or draw the process instead.
4. **Explain:** describe the result in your own words. Separate observation from interpretation.
5. **Reflect:** answer the revision questions without looking, then revisit the objective you
   could not yet explain.

Keep notes concise: a diagram, a few definitions, one example, and one uncertainty are often more
useful than copying a page of text. On lesson pages, the **Mark this lesson complete** control saves
progress locally in your browser.

## Learn each topic by explaining and doing it

For every topic, make sure your notes answer four questions:

1. **What does it mean?** Define the term in plain language, then name its purpose.
2. **How is it different?** Compare it with the closest related idea so the boundary is clear.
3. **What does it look like?** Give a short example and explain what the example does—and does not—show.
4. **How can I practice it safely?** Complete the lesson activity with a diagram, configuration
   checklist, annotated sample, short script, timeline, or report as evidence of your work.

When answering a review question, state the definition first, apply it to the example or scenario,
and explain your reasoning. For investigation questions, separate **observed evidence** from
**interpretation**, identify what remains unknown, and suggest a proportionate next step. A good
answer shows understanding; copying a term or guessing a tool name is not enough.

Use the lesson's worked examples and answer checks to compare your reasoning. If a lesson does not
provide a worked answer for an open-ended prompt, use the four questions above as a self-check and
record any assumptions you made. Practical work must stay within the lesson's stated authorization
and safety boundaries; a synthetic-data or diagram-based alternative is valid practice.

## Set a comfortable pace

There is no required calendar. A useful session can be one lesson, one diagram, or one small
exercise. Pause when a prerequisite is unclear and revisit the earlier phase instead of pushing
through by memorizing terms.

For a learning session:

- Choose one lesson objective.
- Set up only the tools that lesson needs; many activities need none.
- Save a short record of the exercise and the evidence you used.
- End by writing what you know, what you infer, and what you still need to verify.

## Equipment options

- **Reading and diagram path:** complete the explanations, synthetic cases, revision questions,
  and project write-ups without virtual machines.
- **Light lab path:** use one local test system or one isolated virtual machine when a lesson needs it.
- **Multi-system path:** run additional virtual machines only when the project requires them and
  your hardware can support them.

Follow each lesson's safety notes; do not install a tool simply because it appears in a source list.
Use legitimate software sources and avoid personal accounts, credentials, or private documents in
training systems.

## Safe and ethical practice

Authorization is a boundary, not a formality. Practice only on systems, accounts, and data you own
or have explicit permission to use. A system being reachable from the internet does not make it
available for testing. Keep vulnerable virtual machines on an isolated network. Do not use real
credentials or sensitive data in a lab.

When an exercise uses a scenario, synthetic logs, or a provided report, treat that as the intended
practice environment. Do not replace it with a real target. If a lab behaves unexpectedly, stop,
disconnect it from other networks, and return it to its clean state.

## Build a useful portfolio

Save work products rather than screenshots alone. Good examples include:

- A computer, network, or identity-flow diagram.
- A risk register with evidence and defensible prioritization.
- A secure-design checklist and remediation plan.
- A detection rationale and a timeline built from synthetic events.
- A forensic evidence log and report that states limitations.
- A final capstone report and a reflection on what you would investigate next.

Remove personal information, secrets, and real organization details before sharing any work.
Describe your role accurately; distinguish a lab simulation from production experience.

## Checkpoints and self-assessment

Each phase overview states what to learn and links its lessons. Revision pages provide definitions,
comparison prompts, and assessments where available. Some tests are course-created and identified
as such; an answer is not a substitute for explaining the reasoning.

Use these questions at the end of a phase:

1. Can I explain the main ideas without repeating the lesson wording?
2. Can I complete or describe the project using authorized or synthetic data?
3. Can I explain what my evidence supports and what it does not support?
4. Can I suggest a reasonable next step and say why?

If not, revisit the relevant lesson. Progress means building understanding—not merely checking every
box.

## About expertise

This course provides a structured foundation and guided practice. Professional capability develops
through continued study, deliberate practice, feedback, and experience with appropriately authorized
work. No course alone guarantees mastery or job readiness.
